## What's new

- **Sessions on another machine.** Start a Claude Code or Codex session in a folder on a host you reach with ssh, and work in it in a Temple tab like a local one. Add hosts in Settings ▸ Hosts, from your `~/.ssh/config` or by address. **Test connection** lets your own ssh connect and ask what it needs (a host key, a password, a second factor), then checks `claude`, `codex` and tmux on the host and shows what each said. Temple uses your ssh and never stores a password or a key. Start a session from ⌘N (**Folder on <host>…**), the launcher (**New session on <host>…**) or a host project's `+`. Sessions on a host sit under their folder with the host's name beneath it, reopen from the sidebar, ⌘K and History, come back as tabs after a relaunch, and fill a missing title, folder or date from their transcript on the host.
- **Agents on a host keep running when Temple quits.** Each one runs in a hidden tmux server of Temple's own on the host (`tmux -L temple`), so a dropped connection, a sleeping Mac or a quit does not end it, and opening the session again reconnects to it. Closing a tab works as it does locally: an idle agent is stopped, and a working one asks **Detach**, **Stop** or **Cancel**. When you quit, working agents on hosts are detached and keep going, and the quit prompt says which hosts they are on; idle ones are stopped if the host answers in time. Temple never stops anything later on its own: a session it could not stop (the host didn't answer, or another terminal is attached) is left running, and Temple says so.
- **Stopping what is still running.** Settings ▸ Hosts ▸ **Sessions on <host>…** lists every session Temple started on that host and still tracks, with **Stop** and **Keep**; it is also one click from every "left running" notice. From a terminal on the host, `tmux -L temple ls` lists them and `tmux -L temple kill-session -t temple-<handle>` stops one. Temple never lists or stops a session it didn't start, and never touches your own tmux sessions.
- **New Codex sessions on a host are identified, never guessed.** Codex picks its own session ID. When the Codex process Temple started writes its own session file, Temple identifies the session by itself. By default Codex hands that file to its shared app server, so the tab asks "Is this the session?" with the first prompt, the time and the folder, and you answer **Yes, that's it** or **Not this one**. Add `--no-daemon` to Codex's arguments in Settings and Temple identifies the session on its own. Note that those arguments apply to Codex on this Mac too.
- **Codex titles from the first prompt you typed.** Codex sessions written by Codex's shared app server (its default) now title from your first prompt in the sidebar and History, instead of showing "(no prompt)". The instructions block Codex adds for a folder's `AGENTS.md` is never taken for the prompt.
- **⌘W right after a session starts doesn't ask.** A tab whose agent has just started or resumed, and that you haven't typed, pasted or clicked into since, now closes without the "still working" prompt once its title has been quiet for a few seconds. Anything you have sent it since means the usual rule, so ⌘W soon after an answer still asks.

## Known limits

- A host needs tmux 3.2 or newer to start sessions; Test connection says when it doesn't have it. With tmux older than 3.3 (Ubuntu 22.04 ships 3.2a), Codex can't read Temple's colours and uses its default palette, and a drag-selection doesn't reach the Mac clipboard (⇧-drag still selects in Temple's own terminal).
- Claude Code has to be logged in on the host itself. If it isn't, run `claude` there once (in a Temple tab on that host, or in any terminal) and log in.
- Scrollback belongs to tmux on a host: the wheel scrolls tmux's history, and the first key you type returns to the prompt. ⌘F searches what the tab has shown since it connected.
- Quitting stops an agent on a host whose activity dot shows idle. One in a long, silent step can read as idle; reopening the session resumes it from its transcript, but that step is cut short.
- Temple shows only the sessions it started or opened on a host; there is no listing or import of a host's other sessions. Hosts are Linux machines. The usage meter and Reveal in Finder stay on this Mac, and `temple sessions new` starts sessions on this Mac only.

## Upgrading

- Nothing in Temple's database changes. What Temple knows about sessions on hosts lives in a file of its own (`remote-state.sqlite`), and your host list in Temple's settings.
- Settings' Claude and Codex arguments apply on hosts too, `--dangerously-skip-permissions` included.
